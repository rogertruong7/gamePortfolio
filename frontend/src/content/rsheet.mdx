## What it does

RSheet is a spreadsheet with no interface, only a text protocol. Clients send two kinds of command:

```text
set A1 5
set B1 A1 * 2
get B1
```

Pass an address and it listens for TCP connections from many clients. Leave it out and it reads commands from the terminal. Expressions can refer to single cells or to ranges like `A1_A3` and `A1_B2`, which become vectors and matrices. Parsing and evaluation come from the `rsheet_lib` crate, and the concurrency and dependency tracking on top are what I wrote.

## How the threads fit together

1. The main thread accepts connections and spawns one thread for each.
2. All of those threads share the sheet, a `HashMap` of cells behind `Arc<Mutex<...>>`.
3. After a `set`, a connection thread sends the cell's name down an `mpsc` channel.
4. A single background thread reads that channel and recalculates dependants, so a client isn't held up waiting for that work.

## Three problems worth solving

### Not holding the lock while evaluating

Evaluating an expression can be slow, and holding the sheet's mutex for it would freeze every other client. So `set` takes the lock briefly to read its inputs, releases it, evaluates, then takes it again to write the result.

### Out-of-order writes

Releasing the lock creates a race. If two clients set the same cell, the older command might finish last and overwrite the newer one. Each command is timestamped on its connection thread, and before writing, `set` checks whether the stored cell has a later timestamp. If it does, the older result is dropped.

### Recalculating dependants

Each cell stores its expression and the cells it reads. `process_dependencies` finds every cell that depends on the one that changed, rebuilds its inputs, evaluates it again and then recurses, so a change flows down the whole chain.

Errors follow the same path. If a cell can't be evaluated, it stores a `DependsOnErrorCell` error and anything that reads it shows the error too, until the source is fixed.
