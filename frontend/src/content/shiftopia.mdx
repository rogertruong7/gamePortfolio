## What it is

Shiftopia is a workforce scheduling app for convention venues, modelled around ICC Sydney. Managers build rosters, and the app also covers availability, bids and swaps, timesheets and broadcasts. I built it with my UNSW COMP3900 capstone team. The repository sits in a private university organisation, so there's no code link.

The headline feature is shift generation: a manager picks a date and part of the organisation, and the app predicts staffing from that day's events and proposes draft shifts.

## What I worked on

Teammates built the ML service, the demand forecasting and the shift packing algorithm. My work was on either side of them:

- Turning packed shifts into real rows with rule enforcement, in the synthesiser orchestrator
- Rollback, through a `synthesis_runs` table
- The generate shifts screen: demand curves, coverage, gaps, injection preview, projected cost change and compliance warnings
- Dragging shifts across days and subgroups, with a compliance check before each move
- The CI pipeline for the rosters module

## How shift generation works

1. **Fetch events.** Pull the venue events that overlap the selected date.
2. **Map roles.** The models know four role classes: Usher, Security, Food Staff and Supervisor. The database has 77+ job titles, so a priority-ordered regex maps each title to a class, and titles that don't fit are skipped.
3. **Predict.** A FastAPI service runs one XGBoost regressor per class for each event and role pair, using features such as event type, expected attendance and room capacity. The result is a headcount per 30 minute slot.
4. **Find the gap.** Predictions are merged per role and existing shifts are subtracted, leaving residual demand.
5. **Pack shifts.** The packer repeatedly takes the peak slot, widens it to the full demand window, creates a shift and subtracts it.
6. **Apply policy.** Shifts are held between 3 and 12 hours, and supervisor ratios and minimum staffing rules are applied.
7. **Preview and confirm.** Nothing is written until the manager clicks Confirm & Inject.

A day with no events produces no shifts, because the models have nothing to score. The models are trained from the project's seed data, so this demonstrates the pipeline rather than a forecast validated against real rosters.

## The orchestrator

`synthesizeAndInsertShifts` takes the demand for a scope and writes the shifts. Each rule is behind a flag, so the manager can turn supervisor ratios, minimum staffing and duration limits on or off in the generation options. Headcounts are expanded into individual shifts and inserted in chunks of 20.

For rollback, each confirmed run gets a row in `synthesis_runs`, and its shifts carry that run's ID so an undo can find exactly those shifts. There was a catch: the database function that creates shifts has a fixed list of allowed fields and silently dropped the new column. So the orchestrator stamps the run ID onto the rows after inserting them.

I wrote tests for the policy functions, the orchestrator and the confirmation modal.

## Showing the manager what will happen

The timeline shows four series across 27 half-hour slots:

| Series | What it means |
| --- | --- |
| Required | The model's predicted headcount |
| Existing | Current non-cancelled shifts |
| Residual | Required minus existing, never below zero |
| Injection | A dry run of what Confirm & Inject would create |

## CI for a shared codebase

The rosters workflow runs separate jobs for linting, tests and architecture checks. Lint and dependency-cruiser only look at the rosters files changed in the diff, so existing issues elsewhere in a large codebase don't block a change, and lint fixes are committed back to the pull request automatically.
