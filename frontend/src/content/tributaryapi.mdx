## What it is

Tributary is a UNSW assignment that models how an event streaming system like Kafka is put together. It runs in one JVM with everything held in memory, and you drive it from a command line. The repository also has my final UML diagram.

## The model

| Part | What it does |
| --- | --- |
| Topic | A named stream of one event type, split into partitions |
| Partition | A queue of events in the order they arrived |
| Producer | Publishes events to a topic, choosing the partition randomly or manually |
| Consumer group | A set of consumers subscribed to a topic |
| Consumer | Takes events from the partitions allocated to it |
| Event | A generic `Event<T>` with an ID, creation time, payload type, key and value |

## The command line

| Command | What it does |
| --- | --- |
| `create topic <id> <type>` | Creates a topic for `Integer` or `String` events |
| `create partition <topic> <id>` | Adds a partition to a topic |
| `create consumer group <id> <topic> <rebalancing>` | Creates a group on a topic |
| `create consumer <group> <id>` | Adds a consumer and allocates partitions to it |
| `delete consumer <consumer>` | Removes a consumer and frees its partitions |
| `create producer <id> <type> <allocation>` | Creates a random or manual producer |
| `produce event <producer> <topic> <event> [partition]` | Publishes an event loaded from a JSON file |
| `consume event <consumer> <partition>` | Consumes one event |
| `consume events <consumer> <partition> <n>` | Consumes the next `n` events |
| `show topic <topic>` | Prints partitions, their events and connected consumers |
| `show consumer group <group>` | Prints consumers and their partitions |
| `parallel produce (...)` and `parallel consume (...)` | Run several operations on separate threads |

## How it's put together

The CLI calls an `API` class for its operations, which keeps command parsing apart from the core. Inside the core:

- **`Producer` is an interface** with `RandomProducer` and `ManualProducer` implementations, so a new allocation method only needs a new class.
- **`ComponentFactory` creates components.** It picks a producer from the allocation method and a typed event from the payload type.
- **Type checks happen at publish time.** A producer refuses an event that doesn't match its own type or the topic's type.

## Concurrency

Parallel commands start one thread per operation, using `MultiThreadProducer` and `MultiThreadConsumer`. Shared state is guarded with `synchronized` methods on the paths where threads meet: appending to a partition, sending events through a topic and consuming from a consumer.

## What I'd change

- A consumer group stores its rebalancing method, but allocation is simple: a new consumer takes every partition that doesn't have a consumer yet. Partitions don't get redistributed when the group changes.
- Consuming removes the event from the partition queue, so there's no offset to replay from.
- Test coverage is one end-to-end JUnit test that feeds commands into the CLI. I'd test the core directly as well.
