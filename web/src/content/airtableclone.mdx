## What it is

A from-scratch recreation of Airtable's core grid, which I built to learn the T3 stack properly and before coding agents were part of how I work. The live version needs a Google account to sign in.

- **Bases and tables.** Each base holds tables, and a new table starts with sample columns and rows generated by Faker.
- **Inline editing.** Double-click a cell to edit it, and move around with the arrow keys. Changes are saved with an upsert on blur.
- **Views.** Each named view keeps its own sorts, filters and hidden columns.
- **Sort, filter and search.** Sort by several columns, nest AND/OR filter groups using eight operators, and search across every cell.
- **Forms.** A form view, added later, renders an input per column based on its type to create rows.

## The data model

The schema runs from base to table, then to columns, rows and cells. A cell is one row in a `Cell` table, unique on `[columnId, rowId]`, and its value is stored as a string. That makes the schema flexible, but it also means sorting and filtering a table are queries across many cell rows. Most of the interesting work comes from that.

## Paginating a sorted grid

Prisma's query builder couldn't express what the grid needs, so `getInfiniteRowsDB` builds raw SQL. It joins in the sort value for each active sort, then pages with a compound cursor rather than an offset.

For a view sorted by name then notes, "after the last row on this page" becomes:

```sql
(name > :cursorName)
OR (name = :cursorName AND notes > :cursorNotes)
OR (name = :cursorName AND notes = :cursorNotes AND position > :cursorPosition)
```

Each comparison flips to `<` for a descending sort. Row position is the final tie-break, which gives every row a single place in the order, so a page boundary can't repeat or skip rows when values match.

## Filters as a tree

Filter groups reference themselves, so a group can contain conditions and other groups. `buildFilterGroupSQL` walks that tree recursively and produces nested AND/OR clauses:

- `IS`, `CONTAINS` and the other value operators become `EXISTS` subqueries against `Cell`, and their negative forms become `NOT EXISTS`.
- Filter values are passed as bound parameters. The placeholder numbers have to carry on from wherever the search and cursor parameters stopped, which is why the function takes a start index.

## Rendering large tables

TanStack Table handles column state and TanStack Virtual handles the rows, with a fixed 32 pixel row height and an overscan of 40. Rows load 500 to a page through a tRPC infinite query, and the next page is fetched once you scroll within 10,000 pixels of the bottom.

To test this at scale I added bulk inserts for 100,000 and one million rows. The client splits rows into chunks of 500, sends five chunks at a time and shows a progress count. The one million button is disabled in the current build.

## Types, auth and tests

Types flow from the Prisma schema through tRPC to the React Query hooks, and Zod validates inputs at runtime. The routers use tRPC's protected procedure, so signed-out requests are rejected, and the base router checks that you own a base before changing it. Sign-in is Google through NextAuth.

A small Vitest suite with a mocked database client runs in GitHub Actions on every push and pull request.
