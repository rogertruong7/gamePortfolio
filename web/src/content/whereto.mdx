## What it is

Whereto is a mobile app for planning dates and days out. You build a plan as an ordered list of stops, each tied to a place with notes and an estimated time. Once you've been, you can publish a post about it with photos and a caption, and other people can browse it, save it and comment on it.

It's a solo project and still in progress. The code is private for now, so this page is the best description of how it's built.

## How it works

The app has tabs for the feed, explore, creating a plan, your plans, your profile and settings. A typical run through it looks like this:

1. **Create a plan.** Give it a title, description, city and tags, then add stops. Stops have a position, so the order is explicit.
2. **Start the plan.** The backend creates an execution with a status of active, completed or abandoned, and records each stop as you finish it.
3. **Publish a post.** A post is built from the plan and adds a caption and images. The same plan can have several posts.
4. **Browse.** The feed has a "for you" scope and a "following" scope, which only shows posts from people you follow.

## Separating plans from posts

The biggest design change so far was untangling two ideas. At first a single `Plan` entity held both the itinerary and the social content, so routes like `/plans/:id/comments` were really operating on posts. I wrote a design doc, then split it into two models and moved primary keys to UUIDs:

| | Plan | Post |
| --- | --- | --- |
| What it holds | Title, description, city, ordered steps, tags | Caption, cover image, images that can be pinned to a step |
| Purpose | The itinerary, which can stay a draft | The published piece the feed shows |
| Social features | None | Saves and comments |

## The Go backend

The API is written with Fiber and GORM over PostgreSQL, and requests only travel one way: handler, then service, then repository. Handlers deal with HTTP, services hold the rules and repositories hold the queries. DTOs are kept separate from the GORM models, and services return typed errors that handlers turn into status codes.

A few of the rules that live in the service and database layers:

- A plan with no steps can't be started.
- A step can only be completed once per execution, enforced by a unique index. When the completions reach the plan's step count, the execution moves to completed.
- Only the user who started an execution can complete steps on it or abandon it.
- Save counts are updated with a SQL expression rather than read and written back, and a decrement can't take a count below zero.

Auth is my own: bcrypt password hashes with JWT access and refresh tokens. Routes use either required or optional auth middleware, so anyone can read a post while saving one needs an account. Editing or deleting a user goes through an owner-or-admin check.

## The mobile app

The app uses Expo Router for file-based navigation and TanStack Query for server state. An Axios interceptor attaches the access token to each request, and tokens persist in AsyncStorage across launches.

## What isn't finished

- The step-by-step execute screen still runs on placeholder stops. The backend execution API is there, and the plan screen already calls it.
- Cover images are pasted in as URLs. There's no upload yet.
- The config has settings for Cognito, S3 and Redis from the original scaffold, but nothing uses them.
